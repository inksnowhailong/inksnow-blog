# 别再盲目搞“大小模型路由”了：模型体量、显存账本与 Agent 缓存的真实权衡

刚开始折腾本地模型和 Agent 时，我脑子里有两个很朴素的问题：

1. 模型名里的 `1B`、`14B`、`70B` 到底代表什么？它们要吃多少显存？
2. “简单任务走小模型，复杂任务走大模型”听起来很省钱；放进一个长上下文 Agent 里，真的还划算吗？

我拿 16GB 显存的 4070 Ti Super 跑过一阵本地模型，也在长上下文 Agent 里踩过缓存失效的坑。后来发现，很多流传很广的最佳实践都少了一个前提：**请求是一次性的，还是同一条连续会话的一部分？**

这篇把模型体量、显存、推理速度和缓存这几笔账放在一起算。

---

## 1B 到底是什么？16GB 显存能跑多大的模型？

`1B` 是 `1 Billion`，即约 10 亿参数。可以粗略理解为模型训练后保留下来的 10 亿个数；推理时，输入会与这些参数反复做矩阵运算。

参数越多通常意味着模型有更强的知识覆盖和约束处理能力，但“参数数量 = 能力”的关系并不线性。数据质量、架构、训练方式和任务类型同样重要。

权重本身需要的显存可以先这样估算：

| 格式 | 单参数占用 | 1B 参数的典型权重占用 |
| --- | --- | --- |
| FP16 / BF16 | 2 字节 | 约 2GB |
| INT8 | 1 字节 | 约 1GB |
| 4-bit 量化 | 约 0.5 字节，加量化元数据 | 常见约 0.6～0.8GB |

但显卡不是只装权重。真正要算的是：

> **显存占用 = 模型权重 + KV Cache + 推理运行时开销**

KV Cache 会随上下文长度、并发数和模型结构增长。推理模型的长思考输出也会占用更多上下文空间，因此“权重刚好塞得下”通常不等于“这个模型能稳定使用”。

我的经验不是拿 16GB 去硬塞接近 16GB 的权重，而是先留出约 2～3GB 的活动空间。对 16GB 显卡来说：

- `9B` 的 Q8，通常比较从容；
- `14B` 的 Q5/Q6，往往是能力、速度和上下文的甜点区；
- `27B` 的 Q4 有机会启动，但上下文一长就容易陷入显存压力。

这些是估算，不是兼容性承诺。不同量化格式、上下文长度、推理引擎和是否 offload 到 CPU，都会改变结果。

## 模型为什么越大越慢？先分清 Prefill 与 Decode

以前我把“模型大，所以慢”当成一句完整解释。实际推理至少分成两段：

### Prefill：模型先读完你的输入

模型会一次性处理 system prompt、历史消息、代码、工具结果等已有上下文，再生成第一个 token。

这一步主要受输入长度、模型计算量和硬件算力影响。Prompt 越长，首字等待时间越明显。

### Decode：模型一个 token 一个 token 地往外生成

对于常见的稠密模型，生成每个新 token 都要反复访问大量权重。此时瓶颈经常转向显存带宽，而不是峰值算力。

以 4070 Ti Super 约 672GB/s 的显存带宽做直觉估算：权重越大，每生成一个 token 需要搬运的数据通常越多，输出速度就越容易下降。

这也解释了 MoE（混合专家模型）为什么很有吸引力：它可能拥有很大的总参数量，但单次 token 只激活一部分专家。它仍需要容纳大部分权重，显存占用不一定小；但 Decode 阶段实际访问的活跃参数更少，速度可能更接近小模型。

不过别把它当成免费午餐。MoE 的真实速度还会受专家路由、实现质量、batch、显存布局与硬件影响，不能只拿“激活参数量”直接换算 token/s。

## Agent 里盲目切小模型，为什么常常不省钱？

教材式架构很喜欢这样画：

```text
简单分类 / JSON 提取 / 摘要  → 小模型
复杂推理 / 写代码 / 排障      → 大模型
```

对**独立、短上下文、无状态**的请求，这个策略完全合理。

问题出在连续的 Agent 主会话：主模型已经带着很长的上下文在工作时，切到另一个模型处理一个“小任务”，常常是在用看得见的单价节省，交换看不见的缓存、延迟和信息损失。

### 切模型会切断该模型的 Prompt Cache

许多云模型都支持某种形式的前缀缓存：稳定的 system prompt、工具定义和会话历史如果保持前缀一致，就可能复用已经算过的 KV Cache。

命中后的具体折扣、缓存时长和命中条件由供应商决定，不能一概而论；但有一条工程事实很稳定：

> **KV Cache 与具体模型、具体请求前缀绑定，不能从 A 模型直接搬到 B 模型。**

假设主会话已经积累了 50k token：

- 继续调用同一个大模型，并保持前缀稳定：可能命中缓存，少做一大段 Prefill；
- 中途换一个小模型做提取：小模型需要重新读它自己的 50k token 上下文；
- 再切回大模型：如果原会话的缓存已经过期，或前缀被改坏，又得重新读一次。

所以不能只比较“每百万 token 单价”。连续 Agent 的总账至少包括：

```text
总成本 = 输入 token 价格 + 缓存未命中的 Prefill 成本
       + 输出 token 价格 + 延迟 + 失败后的重试成本
```

对长会话而言，**保住主模型的缓存命中率**，常常比临时把某一步换成便宜模型更重要。

如果只是担心大模型在小问题上想太久，优先考虑同一模型内的控制手段：降低 reasoning effort、缩短输出上限、收紧工具调用，或者把简单动作做成确定性代码。具体参数是否影响缓存，仍要以所用供应商的文档和实测为准。

## 小模型做摘要，还有一个更危险的问题：有损

写代码或排障时，最致命的线索经常不在大段正文里，而是一行不起眼的内容：

```ts
// workaround for timezone bug
```

或者一个默认配置、异常分支、版本条件。

让小模型把代码或日志压成 300 字摘要，再交给主模型，看似节省上下文，实际上是在把“未来可能需要的证据”交给一个还不知道后续推理路线的模型删除。

等大模型走到第 5 步才需要那条注释时，它甚至不知道原文里存在过这个线索。

因此在编程 Agent 中，我更认可这样的分工：

> **小模型可以给坐标，主模型必须看到原文。**

小模型或检索器可以做：

- 找相关文件；
- 找符号和调用链；
- 标出行号与片段边界；
- 过滤完全无关的文件。

但进入主会话的关键代码、日志和配置，应尽量保持无损原文，而不是只传二次摘要。

## 小模型真正适合在哪？

“不要在主会话里乱切模型”不等于“小模型没有价值”。它特别适合以下三类工作：

### 1. 极低延迟交互

IDE 自动补全、语音打断、输入预测等场景，要求 100～200ms 级反馈。大模型往往物理上达不到，这时小模型更合适。

### 2. 大批量、短上下文的离线任务

例如夜间给 100 万条评论打标签。每条记录都短、彼此独立，也没有长会话缓存可保护；小模型的成本优势会非常直接。

### 3. 与主会话彻底隔离的旁路清洗

一次工具调用抓回十篇长网页，直接塞进主上下文既慢又污染注意力。这时可以在独立请求中做格式清洗、去重或结构化提取，再把明确结果交回主会话。

关键是“彻底隔离”：它不是主会话中途换脑子，而是一个有清晰输入输出边界的旁路作业。

---

## 最后的决策表

| 场景 | 优先策略 |
| --- | --- |
| 长上下文 Agent 主会话 | 保持同一主模型，尽量保护缓存与原始上下文 |
| 简单确定性动作 | 不用模型，直接写规则或工具 |
| 短、独立、批量任务 | 小模型路由通常划算 |
| 超低延迟交互 | 小模型优先 |
| 大量外部文本进入主会话前 | 旁路清洗；保留关键原文与坐标 |
| 复杂代码排障 | 主模型读原文，小模型只做检索与定位辅助 |

真正该问的不是“这个任务简单不简单”，而是：

> **它是否属于一条需要保持上下文、缓存和推理连续性的主线？**

如果是，先别为了省一点单价把它切碎。主线保缓存、保无损上下文；旁路批处理、重度清洗和极低延迟场景，再让小模型上场。
